SEXTANT — find what to pay for on Stellar

We did not build a payment demo. We built the piece that is missing from x402 on Stellar, and then built the payment demo around it so you can watch the missing piece work.

THE GAP

On Stellar, x402 settlement is already solved. The Apache-2.0 package @x402/stellar ships verify and settle, the exact scheme spec is stable, and the SCF #45 RFP says so in plain language: "settlement on Stellar is largely solved; the novel work is discovery."

Discovery is not solved. An agent that can pay but cannot discover is an agent with a wallet and no map.

The bazaar extension spec defines /discovery/resources and /discovery/search, but it is only a spec. The upstream package @x402/extensions/bazaar states in its own README that it ships only client and server helpers and no facilitator-side catalog implementation. And on the Stellar side, issue #50 in stellar/x402-stellar — "Explore Bazaar support for Stellar" — has been open and unassigned since April 2026. The SDF repository's own Dockerfile still carries the comment "bazaar not used".

SEXTANT is that missing catalog, plus the full vertical loop around it, running end to end on stellar:testnet.

VERIFY IT IN 60 SECONDS

You do not have to trust any claim here. Every one is checkable.

Payments really settle on Stellar: open transaction c1acc578032a3a06a88603f971d871703f45b1246e0f1aa8862500495edbfba6 on stellar.expert and see successful: true. That takes ten seconds.

The buyer needs zero XLM because fees are sponsored: on that same transaction, the fee_account is the facilitator's fee payer, not the payer. Fifteen seconds.

Catalog integrity is real and not decorative: run npm test and get 70 passed, 0 failed, 66 of them adversarial. Thirty seconds.

And you can actually run it: npm install && npm run setup, with no captcha, no faucet and no API key. Two minutes.

That last one is the one we would ask you to weigh most. Nearly every x402-on-Stellar project requires a Circle faucet captcha and an OpenZeppelin Channels API key before it will even start. This one requires neither, by design.

WHAT WE BUILT

A facilitator-side Bazaar index, with spec-exact /discovery/resources and /discovery/search, real BM25 hybrid ranking with a published formula, and a per-result explain breakdown so you can see exactly why a result ranked where it did. It catalogs resources automatically from the discovery extension on settlement, with no separate registration step, applies the spec's soft-drop validation, and reports outcomes in the EXTENSION-RESPONSES header. It catalogs HTTP endpoints and MCP tools side by side, keying MCP tools on the resource.url and input.toolName tuple exactly as the spec requires.

A self-hosted x402 facilitator built on the Apache-2.0 @x402/stellar package, advertising areFeesSponsored, returning a non-null human-readable reason on every rejection, and depending on no third party.

A paid seller API that declares its discovery metadata with per-parameter descriptions, so an agent can construct a valid call without reading any documentation.

An MCP server with four tools carrying both input and output schemas and a seventeen-code error enum, so an agent can search the catalog and pay from inside its own runtime. Real payments were settled through it during development.

And a live console that renders the catalog as a Sight Board with explainable ranking, an animated 402 to sign to settle to 200 payment loop, and a live catalog-integrity ledger showing real timestamped rejections.

TWO BLOCKERS REMOVED BY DESIGN

No faucet and no captcha. Rather than depending on Circle's web faucet for testnet USDC, we issue our own SEP-41 asset called SXT and wrap it in a Stellar Asset Contract. The Stellar exact scheme accepts any SEP-41 token — USDC is only the default. Setup therefore runs start to finish with no web forms.

No AGPL and no third-party facilitator. The facilitator is self-hosted on the Apache-2.0 package, which removes any dependency on the OpenZeppelin Relayer. That relayer is AGPL-3.0-or-later and therefore unusable by any project that needs a permissive license. This is also the self-facilitation path that RFP requirement 3.1 asks for.

THREE CONFORMANCE FINDINGS

We built against the shipped code rather than the documentation, and reading the published dist output turned up three places where the wire format has moved and the surrounding material has not.

First, x402 v2 PaymentRequirements uses amount, not maxAmountRequired, and resource metadata moved to PaymentRequired.resource. The v1 layout is still what most examples show.

Second, v2 signs into the PAYMENT-SIGNATURE header, not X-PAYMENT. X-PAYMENT is the v1 header, and it is still what much of the surrounding documentation instructs.

Third, @x402/core accepts a challenge in the JSON body only for v1; for v2 it expects the PAYMENT-REQUIRED header. A v2 resource server that answers 402 with a body — which is the natural reading — is unreachable by a stock client. Without the fallback we wrote, the paid loop was dead on arrival against our own seller.

That third one is the class of defect that only surfaces when an unmodified client is pointed at an independent server, which is exactly the acceptance test the SCF #45 RFP specifies.

SCOPE, AND WHAT WE DELIBERATELY DID NOT BUILD

SEXTANT is scoped against SCF #45, RFP Track — "X402 Facilitator with Bazaar (discovery) support" — which names the Bazaar discovery layer as the highest-value part of the scope and says it should carry the largest share of the budget. The components here map to requirements 3.1, 3.2, 3.3 and 3.6.

We did not build an on-chain registry, because the RFP itself calls it an optional stretch and explains the rent and TTL burden plus the roughly doubled settlement cost. We did not deploy to mainnet, and we did not get an audit. And we did not implement the upto scheme, because it has an active design discussion opened on 3 August 2026 that deserves a considered answer rather than a rushed one.

Apache-2.0, public from the first commit. Twenty settled testnet transactions, seventy of seventy tests passing, thirty resources indexed.

The point was not to win a weekend. It was to leave behind a piece of public infrastructure that the Stellar ecosystem is currently missing, permissively licensed, that anyone can fork and run.
